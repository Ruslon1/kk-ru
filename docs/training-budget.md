# План ресурсов обучения

Документ фиксирует размер текущего корпуса, параметры трёх конфигураций и
планировочные оценки для `8 x RTX 5090` и `1 x A100`. Источник параметров
обучения — `configs/*.yaml`; исходный код загрузчика данных и цикла обучения —
`src/kk_ru/data.py` и `src/kk_ru/train.py`.

Все точные числа ниже посчитаны по состоянию на 2026-10-05 для файла
`data/filtered/train.kk-ru.tsv` (`6 851 060` строк) и SentencePiece-модели
`data/tokenizer/kk-ru-sp32k.model`, `max_len=256`.

## Токены и проходы по данным

В кэше данных для каждой пары добавляются BOS к source и BOS/EOS к target;
после этого последовательности обрезаются до 256 токенов. Поэтому полезно
разделять три величины:

| Величина | На одну эпоху | За 3 эпохи |
|---|---:|---:|
| Пары предложений | 6 851 060 | 20 553 180 проходов по парам |
| Source-токены (с BOS) | 189 745 655 | 569 236 965 |
| Target-токены (с BOS и EOS) | 207 790 427 | 623 371 281 |
| Все закодированные токены, включая спецтокены | **397 536 082** | **1 192 608 246** |
| Target prediction labels (`tgt[:, 1:]`) | 200 939 367 | 602 818 101 |
| Source + decoder input positions (target сдвинут на одну позицию) | **390 685 022** | **1 172 055 066** |

Для планирования compute основной показатель — target prediction labels и
последняя строка: модель делает примерно **1.172B source+decoder token-операций**
за полный запуск и считает loss примерно по **602.8M target labels**. Padding
внутри динамически собранного batch в эту цифру не входит; фактический compute
будет немного больше. `LengthBatchSampler` сортирует примеры по общей длине,
поэтому padding обычно остаётся небольшим.

Во всех трёх конфигурациях сейчас задано `epochs=3`. Ограничения
`max_len=256`, `dropout=0.1`, `AdamW`, cosine schedule, `label_smoothing=0.1` и
`precision=bf16` одинаковы.

## Конфигурации и batch

`micro_batch_per_gpu` — число пар на одной GPU в одном forward/backward.
`grad_accum` — число таких micro-batch до одного optimizer step.

| Конфиг | Параметры | Precision | Micro-batch / GPU | Grad accumulation | Effective batch на 8 GPU | Effective batch на 1 GPU по YAML |
|---|---:|---|---:|---:|---:|---:|
| `small` | 81 905 024 (~81.9M) | BF16 | 16 | 4 | 512 | 64 |
| `p0` | 202 016 256 (~202.0M) | BF16 | 16 | 4 | 512 | 64 |
| `large` | 578 290 432 (~578.3M) | BF16 | 8 | 8 | 512 | 64 |

На `8 x 5090` конфигурации уже дают одинаковый effective batch `512` пар.
Для сопоставимого запуска на одной A100 лучше сохранить тот же effective batch:

```bash
# small/p0: 16 * 32 = 512
make docker-train MODEL=p0 GPUS=1 OPTS="train.grad_accum=32"

# large: 8 * 64 = 512
make docker-train MODEL=large GPUS=1 OPTS="train.grad_accum=64"
```

Можно увеличить `micro_batch_per_gpu` на A100 и пропорционально уменьшить
`grad_accum`, если калибровочный запуск показывает запас VRAM. Менять effective
batch без отдельного эксперимента не стоит: это меняет число optimizer steps,
длину warmup в терминах данных и поведение scheduler.

### Optimizer steps

Для `6 851 060` строк и текущего `drop_last=True` получается примерно:

| Запуск | Effective batch | Optimizer steps / эпоху | Всего за 3 эпохи | Ожидаемые eval при `eval_every=2000` |
|---|---:|---:|---:|---:|
| 8 GPU, любой конфиг из YAML | 512 | ~13 381 | **~40 143** | ~20 |
| 1 A100, YAML без override | 64 | ~107 048 | **~321 144** | ~160 |
| 1 A100, effective batch выровнен до 512 | 512 | ~13 381 | **~40 143** | ~20 |

Accelerate может дополнить последний shard несколькими примерами для выравнивания
процессов; это даёт разницу в считаные примеры, но не меняет порядок величин.

## VRAM

Обучение использует DDP: каждая GPU держит полную копию модели и optimizer state.
При текущем `bf16` модель и градиенты в базовом расчёте консервативно считаются
как FP32, а два состояния AdamW — тоже FP32. Это даёт около 16 байт на параметр
до учёта активаций и CUDA runtime:

| Конфиг | Параметры | Вес FP32 | Вес + градиенты + AdamW state | Плановый peak на GPU* |
|---|---:|---:|---:|---:|
| `small` | 81.9M | 0.31 GiB | 1.22 GiB | **3–6 GiB** |
| `p0` | 202.0M | 0.75 GiB | 3.01 GiB | **6–10 GiB** |
| `large` | 578.3M | 2.15 GiB | 8.62 GiB | **14–24 GiB** |

\* Peak — это планировочный диапазон для заданного micro-batch и worst-case
`max_len=256`: активации, временные attention-тензоры, DDP buckets и запас
runtime. Это не измерение на конкретной машине. В среднем batch короче 256 и
будет занимать меньше памяти, но резервировать нужно верхнюю границу.

Практический вывод: конфигурации должны помещаться в 32 GiB RTX 5090 и в A100
40/80 GiB. Если реальный peak на длинных batch выходит за этот диапазон, сначала
уменьшаем `micro_batch_per_gpu` в два раза и во столько же увеличиваем
`grad_accum`, сохраняя effective batch.

Перед длинным запуском стоит сделать короткую калибровку на тех же GPU:

```bash
make docker-train MODEL=p0 GPUS=8 \
  OPTS="train.max_steps=100 train.epochs=1 train.save_every=0 train.eval_every=0"
watch -n 1 nvidia-smi
```

Для `large` сначала используйте `micro_batch_per_gpu=8`; при OOM примените
`micro_batch_per_gpu=4 grad_accum=16` на восьми GPU или соответствующий override
на одной A100.

## Время обучения

В репозитории нет замера на RTX 5090 или A100, поэтому это диапазоны для
планирования, а не SLA. Они предполагают CUDA 12.x, BF16, готовый token cache,
обычный DDP и включённые `eval_every=2000`. Первый запуск добавляет несколько
минут на построение кэша; сеть и файловая система могут сделать этот этап дольше.

| Конфиг | 8 x RTX 5090 | 1 x A100 80GB, effective batch 512 |
|---|---:|---:|
| `small` | **~0.75–1.5 ч** | **~2–4 ч** |
| `p0` | **~2–4 ч** | **~5–9 ч** |
| `large` | **~6–12 ч** | **~15–28 ч** |

Диапазон включает обычный запас на DDP scaling, динамический padding и периодическую
оценку на 997 предложениях dev-набора. На одной A100 не используйте YAML без
изменения `grad_accum` для длительного прогона: около 160 eval-прогонов и 321k
optimizer steps делают его существенно дольше при том же количестве данных.

После первых 200–500 optimizer steps время можно уточнить линейной экстраполяцией:

```text
полное время ≈ время калибровки * (целевые optimizer steps / steps калибровки)
```

Калибровку следует проводить с теми же `MODEL`, `GPUS`, batch, precision и
`eval_every`, что и основной запуск; иначе оценка будет смещена.

## Команды запусков

```bash
# Основной прогон на 8 x 5090
make docker-train MODEL=p0 GPUS=8

# Сопоставимый по effective batch прогон на одной A100
make docker-train MODEL=p0 GPUS=1 OPTS="train.grad_accum=32"

# Большая модель
make docker-train MODEL=large GPUS=8
make docker-train MODEL=large GPUS=1 OPTS="train.grad_accum=64"
```

После запуска фактические версии PyTorch/CUDA, список GPU и параметры сохраняются
в `checkpoints/<model>/run_manifest.json` и `resolved_config.yaml`; именно эти
файлы нужно использовать для финального отчёта вместо планировочных диапазонов.
